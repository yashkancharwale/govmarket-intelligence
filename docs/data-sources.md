# Data-source and import configuration

## Current status

The application now contains a **server-side PIB Press Releases RSS adapter**, but it has not collected or persisted live PIB items. A live check returned an empty channel; the adapter is therefore not operationally validated. There are still no connected corporate, social-media, exchange, MCA, or licensed market-data feeds. Existing records are the namespaced, fictional Phase 1 fixtures. The seeded set is 10 fictional official-style profiles, 4 fictional organizations, and 6 fictional events—not representative real-world coverage or the target of approximately 100 real listed companies. Empty provider coverage is reported as unavailable, not as successful ingestion.

## Source adapter boundary

A production adapter should declare a stable source key, type, name, permitted access mode/coverage, authentication and quota requirements. Each run should record start/end timestamps, provider-native ID or cursor, retrieved/new/duplicate/failed counts, retry attempts and provider-reported quota/rate-limit state. Map provider IDs, normalized URLs and content hashes to retained document versions. Do not mark a run successful until fetch, parse, provenance validation and persistence finish.

`shared/intelligence.ts` exports the typed `SourceAdapter`/`SourceDocument` contract and bounded fetch-result metadata. `server/pibRss.ts` implements the fixed PIB feed URL using the existing source, document, event, source-job, and audit tables. The test-only mock remains unconfigured and never fetches or seeds production data. There is no scheduler. Only an authenticated admin can configure, manually run, or export the PIB source; the UI and API require explicit database/source attestations. Server writes also fail closed unless `GOVMARKET_PIB_WRITE_TARGET=development`; this non-secret server setting must only be configured after confirming that the active `DATABASE_URL` points to the intended development/test database. The managed preview/published database may be shared, so do not enable this flag for that shared target. No credentials or user-configurable external URL are needed. Do not add other feeds until their terms, robots policy, supported interface, rate limits, update format, authentication and redistribution rights are checked. Never circumvent logins, CAPTCHA, paywalls or other access restrictions.

Potential future sources specified for the product include PMIndia, official Union ministry/department/scheme portals, data.gov.in, Startup India; supported official public social APIs; NSE/BSE filings, company investor-relations pages and available MCA master data; and an appropriately licensed market-data provider. Listing a source here does not mean the app has access, permission, credentials or redistribution rights.

## PIB press-release RSS: access check and limits

The only source in the current real-ingestion increment is the English, all-India Press Releases RSS feed listed by PIB’s [RSS directory](https://www.pib.gov.in/ViewRss.aspx?lang=1&reg=1): `https://pib.gov.in/RssMain.aspx?ModId=6&Lang=1&Regid=1`. The directory HTML was reachable over HTTPS (HTTP 200) and linked that URL as “Press Releases RSS.” No article-detail pages are fetched by this adapter.

Live access was checked on 2026-10-23. The feed URL returned HTTP 200 with `text/xml`, but its RSS channel contained zero `<item>` elements. This is not a successful ingestion and no feed records were collected during that check. The adapter must treat an empty channel as a failed/unusable run, create no event, and never report a successful live import until items are returned and processed. The requested `https://www.pib.gov.in/robots.txt` path returned HTTP 200 `text/html` with a generic “page not available” response, not usable robots directives; robots policy therefore remains unconfirmed. Do not infer permission from the missing robots file. Recheck the documented endpoint and applicable source conditions before operating the adapter.

PIB’s published [Terms of Use and Copyright Policy](https://archive.pib.gov.in/newsite/terms.aspx) says its website material may be reproduced without prior approval, except third-party material; reproductions should acknowledge PIB prominently, be accurate, and not be used in a misleading or derogatory context. It also disclaims that website content is a statement of law and advises checking with PIB/other sources where ambiguity exists. This does not establish rights over third-party material embedded in a release. Preserve source attribution and the exact item URL, do not republish misleadingly, and leave every imported record unverified until human review.

The PIB adapter is a source-material collector only. It preserves the RSS title, feed description when present, publication timestamp, retrieval timestamp, item URL, and PIB-supplied GUID when present. A missing GUID remains blank in CSV; an internal stable content/URL hash is not exported as a PIB ID. A mention of a company or official is not a verified edge: this adapter creates no company, minister, or other relationship records. Fetched records use `synthetic=false` only to indicate they were fetched from the source; event verification remains `unverified`.

The access check above returned HTTP 200 with a valid RSS 2.0 channel but zero items; its `robots.txt` path returned HTML rather than usable directives. No database row was written during the access check, and the current feed test is not a successful data ingestion. The feed provided no usable publication cursor or `Last-Modified` header, so the adapter refetches the documented feed and relies on GUID/normalized-URL identity plus content hashes for idempotence. The managed development and published application share one database; run administrative configuration or ingestion only when the operator has confirmed the active database is the intended environment.

### PIB adapter operation

Before any write, confirm the active `DATABASE_URL` points to the intended development/test database and set the server-only `GOVMARKET_PIB_WRITE_TARGET=development` flag there; leave the flag unset for shared/production databases. On `/system`, an authenticated admin then checks the database-target acknowledgement, and before fetching confirms current feed access/robots conditions, then enables the fixed source. Configuration itself does not fetch the feed. “Run now” is a manual, admin-only request capped at 500 feed items; the adapter uses HTTPS, follows at most three redirects within the PIB domain, applies a 15-second timeout, caps the XML body at 2 MB, rejects DTD/entity declarations, and makes at most two bounded retries (respecting `Retry-After` up to two seconds). It accepts only RSS XML from the officially documented endpoint. Invalid items are counted; an empty channel, a malformed document, any item/persistence error, or a failed fetch produces a `failed` source job, not a successful one. Job rows retain fetched row count, duplicate count, error count, retry count, quota/rate-limit flag, start/end timestamps and a bounded error summary; `/system` maps per-run new/revision counts from the existing PIB audit details by job ID.

Every event candidate remains `verificationStatus=unverified` and `isSynthetic=false` solely because it was fetched from PIB, not because the assertions were verified. The adapter creates no company, minister, or relationship edges. For this `pib_press_release` candidate type, the feed publication time fills the schema’s required `occurredAt` field; the interface labels it as the feed publication timestamp and explicitly does **not** present it as the date of the underlying government action. The RSS description is retained as source content. A supplied GUID is retained as `externalId`; if absent (or too long for the source ID field), CSV leaves it blank. Internal event identity and document content hashes are not exported as PIB IDs. Same identity/new content creates a retained document revision and event-source evidence snapshot without overwriting an earlier document or the existing event fields.

The admin CSV export contains only PIB-linked, non-synthetic event/document revisions. Its column order is `externalId,eventType,title,occurredAt,category,summary,location,company,minister,sourceType,sourceName,sourceUrl`. It sets `sourceType=government`, `sourceName=Press Information Bureau`, uses ISO timestamps, CSV-quotes commas/quotes/newlines, apostrophe-prefixes spreadsheet-formula-like cells so they open as text, leaves unsupported/inferred fields blank, and preserves the event’s unverified status in the database. Exports are downloaded by the admin and also written to the git-ignored `data/export/pib-press-releases-<timestamp>.csv` path. The server copy is local to the current runtime and may be ephemeral in a published container; retain the browser download if a durable copy is needed. It contains no credentials or private user data.

No migration or seed is required for PIB ingestion. Do not set the write flag, configure, run, or export unless the active `DATABASE_URL` is confirmed to point to the intended development/test database. The application/database may be shared between preview/development and publication; leave the flag unset for a shared/production target. Do not reset, drop, overwrite or delete existing rows.

## CSV import

The `/system` page provides a **server-side admin-only**, audited CSV import. The file must be no larger than 1 MB and contain no more than 1,000 data rows. `title` and ISO `occurredAt` are required. Optional columns are `externalId`, `eventType`, `category`, `summary`, `location`, `company`, `minister`, `sourceType`, `sourceName`, and `sourceUrl`; source types are limited to `fixture`, `government`, `corporate`, `social`, or `market`.

The importer prefers a supplied source-native `externalId`, then a normalized URL, then content hash for identity. Each normalized source name/type/origin maps to a separate user-declared source record. Content is hashed independently of filename. An exact reimport is skipped; changed content is stored as a new document linked to the prior event, with a note that event fields are not auto-overwritten pending review. CSV metadata and URLs remain synthetic/unverified; URLs are not fetched, and a supplied label such as `government` is not evidence that the source is official. Organization and official mentions only create explicitly unverified mention edges when exact canonical/alias matching succeeds; unmatched mentions are retained as unverified entity-resolution candidates. A mention never proves a contract, benefit, or personal relationship.

The CSV flow records per-source job row/duplicate/error totals and an audit record. Row errors are bounded and do not expose database exception text. No operator should convert an imported row into a verified fact without reviewing its supporting source and the specific relationship evidence.

## Provenance and verification

Verification stages are separate values: `unverified`, `machine_matched`, `source_verified`, `independently_corroborated`, and `rejected`. A source document alone does not prove every company/official relationship; event-to-company and event-to-official edges carry their own evidence, status, source/document link and synthetic flag. Keep event verification distinct from edge verification and avoid treating confidence values as measured accuracy.

Synthetic demo events intentionally have no claim to an external real-world source. Evidence panels identify them as fictional fixtures; no fake URL, actual official name, real issuer identity, market quote, CIN, ISIN, NSE symbol or BSE code is supplied as fact.

## Lawful access and restrictions

Respect applicable robots.txt, terms of service, API quotas/authentication/rate limits, copyright, database licenses and Indian law. Do not scrape behind authentication or a paywall, circumvent CAPTCHA or invent endpoints/credentials. Keep raw material only where provider terms permit. Store secrets outside source control and server-render secrets only; never expose them to the browser.
